# LI31: Colony telemetry, what to fix in the product

24 runs (claim, nopeer, market × 8 seeds), gpt-6-luna, 4 worker ants + parent, k=40. All 24 solved (market-s31401 needed a rerun after a provider error, see `provider-error/`). Figures are per-run means unless marked.

## Summary

- **Model time takes the wall clock, and the parent is the bottleneck.** Tool execution is about 2 to 3 min of each run (bash about 130 s). The rest is model turns. The parent is busy for 73% of the wall time in claim (867 s of 1,194 s). On average only 2.2 of the 4 ants are working at once (1.8 in market). Messages wait in queues: the median wait is 137 s for a message to the parent and 217 s for a message to an ant in claim (120 s / 95 s in market). There is no time when nobody is working. The last ~200 s of every run (17–24% of wall) is the lab driver's quiet window, not Colony work.
- **Queued messages are delivered one per turn.** `flushAnts` shifts a single item. When a queued message is delivered, a median of 8 more are already waiting for the same recipient (p90 23, max 46).
- **The parent mostly re-runs the test suite.** In claim, 50 of its 79 turns per run do nothing but `node test/run.mjs`. 46 of those get output identical to its previous run. Those turns cost 13.4M tokens per run, 28% of all claim tokens (37% in market).
- **Why the field arms cost about 2× market (47.9M vs 24.0M tokens, [US$ redacted] vs [US$ redacted]).** Two thirds of the extra 23.9M is ants: +38 ant turns per run (87 vs 49), and each ant turn costs 316k vs 231k tokens. 43 of those ant turns per run are started by field traces, and 18.4 traces per claim run are "I adapt, keep yours" notices that need no change from the recipient. The other third is the parent: +29 turns, driven by +29 ant→parent reports.
- **The parent's context is always nearly full.** Its peak is 93% of the 272k window in 24/24 runs, with 31 parent compactions in total (each from about 258k down to about 28k). Every parent wake re-sends about 255k tokens (97% cached).
- **Wasted reads are not a problem.** Ants re-read an unchanged file about 15 times per claim run (about 9 KB). There are only about 1.75 edit errors per run.

## Method

- Data: the 24 `*.export.json` files and the `<arm>-s<seed>.json` summaries in this folder; `run.log`; `provider-error/`. Context from `~/misc/colony` (`tasks.cjs` `antCharge`/`deliverAnt`/`flushAnts`/`fieldTrace`/`checkStalls`, `ants.cjs`, `executor.cjs`, `lab-export.cjs`) and the lab driver `observatory/batch2/colony/drive.mjs`.
- Scripts: two local node scripts (not kept in the repo) plus a few inline `node -e` passes. They computed:
  - turn intervals (`at` is the end of a turn, so start = `at − durationMs`) and the union of busy time per role;
  - per-arm token and cost splits for the parent vs ants;
  - tool error clusters (digits normalised);
  - depth of the delivery queue and possible batching (a message enqueued before the previous delivery to the same recipient started);
  - parent turns classified by the set of tools they used, and test re-runs with no write or edit (or `sed -i`/redirect into `src/`) since the same chat's last run;
  - repeated reads of the same path and range with no write in between;
  - claim notice vs change request (regex on `need`);
  - `field_read` results that were empty;
  - stalls ("Parei de responder"), compactions and context peaks.
- Caveats: `out` is cut at 2,000 chars, so output sizes are lower bounds. The batching estimate (claim 163 deliveries → about 33 turn starts per run) is an upper bound because timing would shift. Token totals count cached input; about 97% of input was cached, so the dollar cost is much lower than the token volume suggests.
